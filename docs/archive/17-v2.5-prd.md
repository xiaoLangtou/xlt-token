# xlt-token v2.5 产品需求文档

> **版本：** v2.5  
> **基线版本：** v2.4.0  
> **状态：** 待立项  
> **关联文档：** [v2.2+ 执行路线图](./14-v2-next-execution-roadmap.md)、[JWT 策略](../core/jwt-strategy.md)、[Redis Store 指南](../store-redis/index.md)、[多实例与适配器契约](../guide/multi-instance-contract.md)

## 1. 概述

v2.5 聚焦两条主线：

1. **JWT 密钥运维**：把 JWT 密钥从启动时静态配置（`createJwtStrategyConfig({ activeKid, keys })`）扩展为支持从 JWKS 端点动态装载与缓存公钥，配套密钥轮换监控、按 `kid` 的 Token 失效与密钥使用审计。
2. **Store 生态**：冻结 Store 能力矩阵（原子消费、TTL、分页扫描、批量操作、事务），交付 PostgreSQL、MongoDB、KeyDB/Valkey 三个官方 Store，并让所有实现（含既有 MemoryStore、RedisStore、IORedisStore）通过同一套 `@xlt-token/store-contract` 契约测试。

Core 与 `@xlt-token/jwt` 不引入 JWKS 拉取或数据库驱动的运行时依赖；数据库客户端沿用 `@xlt-token/store-redis` 的可选 peer dependency 模式。

| SDK 使用者 | 接入 JWKS 或新 Store | 需要清晰的安装、配置、能力边界与降级行为说明。 |

## 3. 背景

**JWT 现状**：密钥在启动时通过 `createJwtStrategyConfig({ activeKid, keys })` 静态给定，`JwtStrategy.verifyToken()` 解码后按 `header.kid` 在静态 `keys` Map 中查找，未配置时抛出 `JWT key "<kid>" is not configured`。算法白名单（HS256/384/512、RS256/384/512、ES256/384/512）已覆盖 JWKS 适用的非对称算法，但缺少运行时密钥装载：与外部 IdP 或集中签发服务协作时，密钥轮换需要重启应用。按 `kid` 批量失效、密钥使用审计目前均无官方能力。

**Store 现状**：`XltTokenStore` 契约包含 `get` / `set` / `delete` / `getAndDelete`（v2.2 冻结的原子消费）/ `setIfAbsent` / `compareAndSet` / `compareAndDelete` / `touch` / `scan` 九个操作。官方实现为 MemoryStore（core 内）与 RedisStore / IORedisStore（`@xlt-token/store-redis`，数据库客户端为可选 peer dependencies）。`@xlt-token/store-contract` 的 `defineStoreContract(name, createStore)` 已是共享契约测试的唯一入口。但各实现的语义差异（SCAN 游标、TTL 返回、事务边界、批量能力）散落在文档中，没有正式的能力矩阵；使用 PostgreSQL / MongoDB 技术栈的团队必须自研 Store。

## 4. 目标

### 产品目标

1. 服务可以从 JWKS 端点按 `kid` 动态装载验证公钥，密钥轮换不需要重启应用，也不需要手工维护静态 `keys`。
2. 密钥运维可控可观测：轮换自动检测、按 `kid` 失效、密钥使用审计，且 JWKS 端点不可用时的行为可预测、可配置、可观测。
3. 使用 PostgreSQL、MongoDB 或 KeyDB/Valkey 的团队可以直接使用官方 Store，全部实现满足同一套原子语义契约。
4. 自定义 Store 有权威的能力矩阵与参考文档，官方与社区实现的行为边界一致。

| 编号 | 结果 | 度量方式 |

## 5. 用户细分

| 用户任务 | 主要问题 | 约束 |
| --- | --- | --- |
| 验证外部 IdP / 集中签发服务签发的 JWT | 无法动态获取验证公钥，轮换需重启。 | 不得引入第三方 JOSE 依赖；算法白名单必须继续生效。 |
| 密钥运维与安全审计 | 无按 `kid` 失效与密钥使用审计能力。 | 审计不得记录原始 Token 或密钥材料。 |
| 已有 PostgreSQL / MongoDB 运维栈的团队 | 必须额外维护 Redis 或自研 Store。 | 原子语义必须与 Redis 实现一致。 |
| 使用 KeyDB / Valkey 的团队 | 官方支持矩阵未声明协议兼容范围。 | 复用 Redis 协议兼容层并显式声明差异点。 |
| Store 贡献者 | 缺少能力矩阵与参考实现文档。 | 契约测试是唯一验收入口。 |

| 用户收益 | v2.5 提供的价值 |
| --- | --- |
| 零重启密钥轮换 | JWKS 端点 + TTL 缓存 + 轮换监控，轮换由签发方自主推进。 |
| 可控的故障边界 | 端点不可用时缓存、拒绝与降级行为由设计文档明确规定，不静默失效。 |
| 精准的密钥处置 | 按 `kid` 失效可在密钥疑似泄露时快速止血，撤销记录与 `kid` 关联可审计。 |
| 存储栈自由 | PostgreSQL / MongoDB / KeyDB/Valkey 官方 Store 与 Redis 实现语义一致。 |
| 一致的生态契约 | 能力矩阵 + 同一套契约测试，官方与自定义 Store 行为可预期。 |

## 7. 解决方案

### 7.1 用户流程

```text
应用启动
  ├── createJwksKeySource({ url, cacheTtlSeconds, refreshIntervalSeconds, ... })
  │       └── 拉取 JWKS → 校验 kty/alg 白名单 → 按 kid 建立缓存索引
  ├── createJwtStrategyConfig({ activeKid?, keys?, keySource?, ... })
  │       └── JwtStrategy.verifyToken(): header.kid → 缓存查询 → miss 时受控刷新一次
  └── revokeJwtKid(kid) / restoreJwtKid(kid)
          └── 撤销记录写入 XltTokenStore → verify 拒绝该 kid 的全部 Token

createPostgresStore(pool) / createMongoDbStore(database) / createValkeyStore(client)
  └── 全部接入 defineStoreContract 同一契约测试
```

### 7.2 功能需求

#### JWT 密钥运维

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| R1.1 | 新增 JWKS KeySource 抽象，`JwtStrategy` 支持从 KeySource 按 `kid` 解析验证密钥；静态 `keys` 配置保持不变并继续可用。 | 既有静态配置测试零改动通过；KeySource 与静态 keys 可并存（静态优先或显式声明优先级）。 |
| R1.2 | `createJwksKeySource()` 从 JWKS 端点读取公钥集合，按 `kid` 建立缓存索引，TTL 可配置。 | 缓存命中不产生网络请求；TTL 过期后重新拉取。 |
| R1.3 | 仅装载非对称算法（RS\*、ES\*）；`kty` / `alg` 不在白名单内的 key 拒绝装载；JWKS 中的 HS\* 共享密钥必须显式拒绝。 | 恶意 JWKS（含 oct 密钥或未知算法）在装载期报错，不进入缓存。 |
| R1.4 | `verifyToken()` 缓存 miss（未知 `kid`）时触发一次受控刷新，并发 miss 只允许一个网络请求。 | 并发未知 `kid` 验证只产生一次 JWKS 拉取；刷新后仍 miss 保持既有错误语义。 |
| R2.1 | 周期性检测 JWKS 更新并自动刷新缓存；新增 `kid` 可即时可用，移除的 `kid` 具备可配置的保留宽限。 | 轮换场景（新增 + 移除 + active 切换）集成测试通过；宽限期内旧 `kid` 验证行为符合 design 规定。 |
| R2.2 | 轮换、刷新失败、key 移除等密钥事件接入 `XltEventSink` 审计事件（新增 `key.*` 事件类型），事件不含密钥材料。 | 事件字段仅含 `kid`、算法、动作与结果；脱敏回归测试通过。 |
| R3.1 | 提供按 `kid` 的 Token 失效能力：撤销记录与 `kid` 关联并持久化到 `XltTokenStore`，verify 阶段拒绝已撤销 `kid` 的 Token。 | 撤销后该 `kid` 全部 Token 验证失败；恢复 / TTL 过期后可再次验证；与既有 Token family 撤销和 JWT 登出黑名单键空间不冲突。 |
| R3.2 | 按 `kid` 失效产生审计事件，可区分按 Token、按 family、按 `kid` 三种撤销来源。 | 审计事件测试覆盖三种来源。 |
| R4.1 | 提供密钥使用审计：记录用于签发或验证的 `kid`、算法与结果；事件频率可控（支持采样或事件开关），不产生每请求事件风暴。 | 默认配置下无每请求事件；开启后事件字段稳定且不含原始 Token。 |
| R5.1 | design 文档明确 JWKS 端点不可用时的安全策略：缓存 stale 允许窗口、首次获取失败的拒绝条件（默认 fail-closed）、刷新失败的降级行为与恢复策略。 | 实现与 design 一致；故障注入测试覆盖启动期失败、运行期刷新失败、stale 窗口内验证三类场景。 |
| R5.2 | 不可用与降级状态可观测：产生审计事件与可轮询的健康状态。 | 状态查询 API / 事件在故障注入测试中可观测。 |

#### Store 生态

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| R6.1 | 冻结 Store 五维能力矩阵：原子消费（`getAndDelete`）、TTL、分页扫描（`scan`）、批量操作、事务支持；明确每维的判定标准与契约断言归属。 | 能力矩阵规范进入 `@xlt-token/store-contract` 文档；每维对应可执行的契约断言或显式豁免声明。 |

| R7.1 | 新增 `@xlt-token/store-postgresql`，`pg` 客户端为可选 peer dependency。 | 原子操作（`getAndDelete`、`setIfAbsent`、CAS 系列）使用单语句或事务保证原子性；通过 `defineStoreContract` 全量契约测试。 |

| R8.1 | 新增 `@xlt-token/store-mongodb`，`mongodb` 驱动为可选 peer dependency。 | `getAndDelete` 使用 `findOneAndDelete` 等原子操作；通过 `defineStoreContract` 全量契约测试。 |
| R9.1 | 新增 `@xlt-token/store-valkey`，复用 `@xlt-token/store-redis` 的协议兼容层与命令映射。 | 通过 `defineStoreContract` 全量契约测试；与 Redis 实现的差异点（GETDEL / EVAL / SCAN 版本支持）在文档中显式声明。 |
| R10.1 | 同一套 `defineStoreContract` 契约测试运行全部官方实现（Memory、Redis、IORedis、PostgreSQL、MongoDB、Valkey）。 | CI 矩阵全绿；契约测试新增维度同步覆盖既有实现。 |
| R10.2 | 编写官方参考实现文档：自定义 Store 接入方式、`defineStoreContract` 使用方法、能力矩阵声明模板。 | 文档包含可运行的接入示例与契约测试接线示例。 |

### 7.3 技术与质量约束

- Core 与 `@xlt-token/jwt` 不引入 JWKS 拉取、JOSE 或数据库驱动依赖：JWKS 拉取使用全局 `fetch`，JWK 导入使用 `node:crypto`（`createPublicKey({ format: "jwk" })`）。
- PostgreSQL / MongoDB / Valkey 客户端一律为可选 peer dependencies，沿用 `@xlt-token/store-redis` 模式（`peerDependenciesMeta.optional`）。
- 审计事件遵循既有脱敏边界：只包含 `kid`、算法、动作与结果，不包含原始 Token、密钥材料与 JWKS 响应原文。
- 算法白名单与 HMAC 密钥强度校验（≥32 字节）保持不变。
- 按 `kid` 撤销的键空间设计必须与既有黑名单 / Token family 撤销键空间隔离，并在 design 中给出键命名规范。
- 所有公开包遵循工作区双模块构建、类型检查、包边界、安全检查与发布干跑要求；新包进入发布门禁的版本一致性检查。

### 7.4 非范围

- OAuth2/OIDC 客户端集成、IdP 发现与动态注册（v3.0 范围）。
- KMS / 密钥托管集成与 X.509 证书链校验（仅支持标准 JWKS 格式）。
- 跨 Store 数据迁移工具与双写方案。
- 修改既有 `XltTokenStore` 九个操作的方法签名与语义（v2.2 `getAndDelete` 契约保持不变）；批量操作通过能力矩阵以可选能力渐进引入。
- Hono 适配器、会话管理增强（v2.4 范围）与限流、设备指纹等安全策略扩展（v2.6 范围）。

### 7.5 假设与待验证项

| 假设 | 验证方式 |
| --- | --- |
| 全局 `fetch` + `node:crypto` 的 JWK 导入足以解析标准 JWKS，无需第三方 JOSE 库。 | RS256 / ES256 真实 JWKS 样本解析与验证测试。 |
| Valkey / KeyDB 对 `GETDEL`、`EVAL`、`SCAN` 的协议兼容度足以复用 Redis 命令映射。 | 在真实 Valkey / KeyDB 实例上运行同一契约测试并记录差异。 |
| PostgreSQL / MongoDB 无内建 TTL，读取时惰性过期 + `expiresAt` 语义可满足契约。 | 过期读写契约测试 + design 文档明确清理策略建议。 |
| 按 `kid` 撤销的键空间与既有黑名单 / family 撤销不冲突。 | 键命名规范评审 + 集成测试。 |
| 密钥使用审计的默认频率策略（默认关闭 / 采样）满足审计需求且不产生事件风暴。 | 审计事件负载测试。 |

## 8. 发布计划

v2.5 按四个递进阶段交付；Store 线与 JWT 线可并行推进，预计两个短迭代完成。

| 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| 阶段一：能力矩阵冻结 | R6.1 / R6.2：能力矩阵规范、契约断言补充、既有三实现矩阵声明。 | 能力矩阵进入 `@xlt-token/store-contract`；既有实现通过新增断言或显式豁免。 |
| 阶段二：新 Store 交付 | R7 / R8 / R9 / R10.1：PostgreSQL、MongoDB、Valkey 三个 Store + 契约测试矩阵。 | 三个新包通过 `defineStoreContract` 全量契约测试，发布干跑通过。 |
| 阶段三：JWKS 与密钥运维 | R1–R5：KeySource、轮换监控、按 `kid` 失效、密钥审计与不可用安全策略。 | KR1–KR3 验收测试通过，design 文档冻结。 |
| 阶段四：文档与发布 | R10.2：自定义 Store 参考文档、JWT 策略文档更新、CHANGELOG、发布说明与发布干跑。 | 全部质量门禁与发布检查清单通过。 |

首个 v2.5 版本包含 R1–R10 全部需求。若 JWKS 安全策略 design 未冻结，则该阶段单独顺延，不阻塞 Store 线发布。
