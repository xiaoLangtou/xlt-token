# xlt-token v2.2 产品需求文档

> **版本：** v2.2  
> **基线版本：** v2.1.1  
> **状态：** 已交付（2026-09-01，v2.2.0）  
> **关联路线图：** [v2.2+ 执行路线图](./14-v2-next-execution-roadmap.md)

## 背景

xlt-token 已完成 Core、JWT、Redis、NestJS 与 Express 的主要认证能力。后续要接入原生 Fastify 和 Hono 时，现有的全局 `StpUtil` 绑定方式与同步 Cookie 抽象会直接影响适配器的 API、状态隔离和运行时能力。

v2.2 不提前开发新适配器。该版本先完成发布治理收口，冻结多实例和 Cookie 两项架构决策，并提供可在现有生态中立即使用的临时 Token 原子消费能力。

## 产品目标

1. 为后续 Fastify/Hono 适配器建立稳定的实例化契约，避免适配器依赖全局单例。
2. 明确 Cookie 同步/异步模型和各运行时支持矩阵，避免不受支持的配置产生不明确行为。
3. 使临时 Token 支持“读取即销毁”，满足一次性邀请、密码重置和短期授权链接的并发安全要求。
4. 在两天内收口已完成的 OpenSpec 变更和发布治理流程，避免治理项挤占功能迭代。

## 成功标准

| 目标 | 可验证结果 |
| --- | --- |
| 多实例契约 | 设计文档和类型草案定义实例创建、适配器输入、默认实例与兼容策略；后续适配器不需要读取 `StpUtil`。 |
| Cookie 决策 | 团队只保留一个明确方案；支持矩阵、文档与运行时校验遵循该方案。 |
| 原子消费 | 同一临时 Token 的并发消费中恰好一个调用返回业务值，其他调用返回 `null`。 |
| Store 一致性 | MemoryStore、RedisStore、IORedisStore 通过同一套原子读取并删除契约测试。 |
| 发布治理 | 三项已完成 OpenSpec 变更完成归档；发布检查清单和 CHANGELOG 流程可执行。 |

## 用户与使用场景

| 用户 | 场景 | 需要的结果 |
| --- | --- | --- |
| SDK 使用者 | 创建一次性重置密码或下载链接 | 链接首次消费后立即失效，重复访问不能再次获得业务数据。 |
| 框架适配器开发者 | 开发 Fastify/Hono 插件 | 插件接收明确的认证实例，不受其他应用实例影响。 |
| 使用 Hono/Elysia 的开发者 | 配置 Token 来源 | 在启动或初始化时得到明确的能力限制，而不是在请求期间产生不确定结果。 |
| 发布维护者 | 发布 v2.2 | 按统一检查清单完成质量验证、变更说明和发布干跑。 |

### R4：临时 Token 原子消费

#### 用户行为

业务服务调用 `consumeTempToken(tempToken)` 消费一次性 Token。方法在 Token 有效且未被消费时返回关联业务值，并在同一原子操作中删除存储记录；Token 不存在、已过期或已消费时返回 `null`。

#### API 与存储契约

| 层级 | 需求 |
| --- | --- |
| Core | 在 `StpLogic` 与 `StpUtil` 提供 `consumeTempToken(tempToken): Promise<string \| null>`。 |
| Store | 新增原子读取并删除方法，例如 `getAndDelete(key): Promise<StoreEntry \| null>`；最终名称由 OpenSpec proposal 冻结。 |
| MemoryStore | 在同一临界段完成读取和删除。 |
| RedisStore / IORedisStore | 使用 Redis 原子命令或 Lua 完成读取和删除，并保持 Store 契约返回格式一致。 |
| 兼容性 | 保留 `parseTempToken` 与 `deleteTempToken` 的现有行为。 |

#### 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 首次消费有效 Token | 返回原始关联值，Token 立即失效。 |
| 再次消费同一 Token | 返回 `null`。 |
| 并发消费同一 Token | 恰好一个调用返回关联值。 |
| 消费过期 Token | 返回 `null`。 |
| UUID 与 JWT 策略 | 两种策略下行为一致。 |
| Memory 与 Redis Store | 通过同一套契约测试。 |

## 非功能需求

| 分类 | 要求 |
| --- | --- |
| 兼容性 | v2.2 不移除或改变现有公开 API 的行为。 |
| 安全性 | 原子消费不得暴露原始 Token 到事件、日志或异常消息中。 |
| 一致性 | Store 接口语义必须独立于存储后端；未来 Store 能复用同一测试套件。 |
| 可测试性 | 新增 Core 逻辑必须有单元测试；Store 变更必须有共享契约测试；适配器限制必须有配置级测试。 |
| 工程质量 | 通过仓库的格式、静态检查、类型检查、测试、构建与发布干跑门禁。 |

## 风险与处理原则

| 风险 | 处理原则 |
| --- | --- |
| 多实例设计影响现有静态 API | v2.2 先交付兼容设计；任何实际 API 变更都通过独立 OpenSpec 评审。 |
| 异步 Cookie 影响面过大 | 用 R3 的决策记录确定版本边界；不在未决状态下开发 Hono Cookie 支持。 |
| Redis 版本差异 | 在 Store proposal 中明确原子命令与兼容范围，并用共享契约测试验证。 |
| 发布治理无限扩张 | R1 严格执行两天时间盒，非阻塞项转为独立 backlog。 |
