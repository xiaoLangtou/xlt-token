# xlt-token v2.3 产品需求文档

> **版本：** v2.3  
> **基线版本：** v2.2.0  
> **状态：** 待立项  
> **关联文档：** [v2.2+ 执行路线图](./14-v2-next-execution-roadmap.md)、[多实例与适配器契约](../guide/multi-instance-contract.md)、[Cookie 契约决策](../guide/cookie-contract.md)

## 1. 概述

v2.3 为纯 Fastify 应用提供官方认证适配器，并把现有脱敏审计事件接入可选的 OpenTelemetry、结构化日志和指标示例。该版本先将 v2.2 冻结的多实例类型草案落实为 Core 公开 API，再让 Fastify 适配器只依赖显式认证实例。

开发者可以在不引入 NestJS 的情况下使用 xlt-token，也可以把登录、刷新、下线等认证事件接入已有观测平台。Core 保持不依赖 Fastify、OpenTelemetry 或日志实现。

## 2. 相关角色

| 角色 | 责任 | 备注 |
| --- | --- | --- |
| 产品与版本维护者 | 确认范围、发布节奏与变更说明 | v2.3 不扩展到 Hono 或管理 API。 |
| Core 维护者 | 落实实例化公开 API 与 `StpUtil` 兼容语义 | 通过 `core-instance-contract` OpenSpec 变更推进。 |
| Fastify 适配器维护者 | 开发、测试和发布 `@xlt-token/fastify` | 必须使用显式 `XltInstance`。 |
| 可观测性维护者 | 开发事件导出器与接入示例 | 必须保持事件脱敏。 |
| SDK 使用者 | 集成 Fastify 或导出认证事件 | 需要清晰的安装、配置和能力边界。 |

## 3. 背景

当前项目已经提供 NestJS（含 Nest Fastify 平台）和 Express 集成，但纯 Fastify 用户仍需自行桥接 Core。v2.2 已冻结实例化契约：后续适配器必须接收显式 `XltInstance`，禁止依赖 `StpUtil` 或默认实例。

v2.2 同时确定 v2.x 保持同步 `HttpCookies` 契约。Fastify 使用同步 Cookie 插件，可在注册 `@fastify/cookie` 后支持 Cookie Token 来源；Hono/Elysia 的 Header/Query 限制留给 v2.4 处理。

Core 已产生脱敏 `XltAuditEvent`，但用户需要自行把事件转换为追踪、日志和指标。v2.3 提供独立导出器和示例，让认证行为可以进入已有观测链路。

## 4. 目标

### 产品目标

1. 让纯 Fastify 用户可以通过官方包完成登录、登录校验、权限、角色与二级认证，不依赖 NestJS。
2. 将多实例契约落实为可发布的 Core API，确保多个认证实例可以在同一进程中独立使用。
3. 让 `XltEventSink` 可以接入 OpenTelemetry、结构化日志和指标示例，同时保持审计事件脱敏边界。

### 关键结果

| 编号 | 结果 | 度量方式 |
| --- | --- | --- |
| KR1 | v2.3 发布前，`@xlt-token/fastify` 通过全部单元、类型和 E2E 测试。 | CI 与发布检查全绿。 |
| KR2 | Fastify 适配器在 Header、Query、Cookie、权限、角色、Safe、JWT、Redis 场景均有自动化覆盖。 | 每个场景至少一条 E2E。 |
| KR3 | 所有适配器入口都接收显式 `XltInstance`，且没有适配器内核代码读取 `StpUtil`。 | 静态边界检查与测试通过。 |
| KR4 | 每个 `XltAuditEventType` 都能映射到日志或 OTel 事件，且测试确认不包含原始 Token。 | 导出器单元测试通过。 |
| KR5 | v2.2 的 NestJS、Express 与 `StpUtil` 用法保持兼容。 | 既有工作区测试全绿。 |

## 5. 用户细分

| 用户任务 | 主要问题 | 约束 |
| --- | --- | --- |
| 在 Fastify 中接入认证 | 需要手写 Core 到 Fastify 的请求桥接和路由策略。 | 需要保留 Fastify 的 Plugin、Hook 与路由配置习惯。 |
| 在同一进程托管多个服务 | 默认静态实例可能被后创建的应用覆盖。 | 现有 `StpUtil` 用户不能被强制迁移。 |
| 把认证事件送入监控平台 | 需要逐一转换审计事件、字段与脱敏规则。 | Core 不能引入 OTel、日志 SDK 或 exporter 依赖。 |
| 评估官方适配器能力 | Cookie、JWT、Redis 和路由策略支持范围不够直观。 | 文档必须与运行时行为一致。 |

## 6. 价值主张

| 用户收益 | v2.3 提供的价值 |
| --- | --- |
| 官方 Fastify 集成 | 使用 Plugin 和 Hook 接入，不再维护自定义桥接层。 |
| 安全的实例隔离 | 每个适配器绑定明确的认证实例，多应用不会依赖全局状态。 |
| 一致的授权体验 | Fastify 的登录、权限、角色和 Safe 语义与 Express/NestJS 对齐。 |
| 可用的审计数据 | 复用脱敏事件，快速接入日志、追踪和认证指标。 |
| 清晰边界 | README、类型与错误信息明确说明 Cookie 前置条件与支持矩阵。 |

## 7. 解决方案

### 7.1 用户流程

```text
应用创建 XltInstance
        │
        ├── app.register(xltFastifyPlugin, { instance, ... })
        │       │
        │       └── Hook 读取 Token → Core 校验 → 写入 request 认证状态
        │
        └── createOpenTelemetryEventSink / createLoggerEventSink
                │
                └── XltEventSink 接收脱敏事件 → 日志、追踪或指标系统
```

### 7.2 功能需求

#### R1：实例化 Core 契约

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| R1.1 | 实现 `XltInstance` 和 `createXltInstance()`。 | 创建实例不会隐式修改默认实例。 |
| R1.2 | 提供 `setDefaultXltInstance()` 与 `getDefaultXltInstance()`。 | 默认实例只能显式设置；未设置时静态门面提供清晰初始化错误。 |
| R1.3 | 保留 `createXltToken()` 与 `StpUtil` 兼容路径。 | 既有 NestJS/Express 测试和示例无需改写。 |
| R1.4 | 建立包边界。 | Fastify 与观测性包只使用 Core 的公开类型和 API。 |

#### R2：原生 Fastify 适配器

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| R2.1 | 新增 `@xlt-token/fastify` workspace 包。 | 包可独立安装，产出 ESM、CJS 和类型声明。 |
| R2.2 | 提供 `xltFastifyPlugin`。 | Plugin 需要显式 `instance`，缺失实例在注册阶段明确报错。 |
| R2.3 | 建立 Fastify `HttpContext` 桥接。 | 支持 Header、Query、响应 Header；注册 `@fastify/cookie` 后支持 Cookie。 |
| R2.4 | 接入 Hook 与路由策略。 | 使用 `preHandler` 完成登录校验；路由配置支持 ignore、登录、权限、角色和 Safe。 |
| R2.5 | 写入请求认证状态。 | Fastify request 类型包含 `stpLoginId`、`stpToken` 与可选 `stpSession`。 |
| R2.6 | 提供用户文档与示例。 | 示例覆盖 UUID、JWT、MemoryStore、Redis 和 Cookie 前置条件。 |

#### R3：可观测性导出器

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| R3.1 | 新增独立可观测性包。 | Core 不新增 OpenTelemetry 或日志 SDK 依赖。 |
| R3.2 | 提供 `createOpenTelemetryEventSink()`。 | 将所有 `XltAuditEventType` 映射为稳定事件名和属性。 |
| R3.3 | 提供 `createLoggerEventSink()` 与 `composeEventSinks()`。 | 用户可以接入任意满足接口的结构化 logger，也可以组合多个 sink。 |
| R3.4 | 提供指标示例。 | 示例展示登录成功率、刷新次数与认证异常事件计数。 |
| R3.5 | 保持脱敏与异常隔离。 | 导出数据不包含原始 Token；导出器故障不改变认证结果。 |

### 7.3 技术与质量约束

- Fastify 适配器只能使用显式 `XltInstance`，不得读取 `StpUtil` 或默认实例。
- Fastify Cookie 模式依赖 `@fastify/cookie`；未注册时必须在配置阶段给出明确错误。
- Fastify 的授权规则与 Express/NestJS 保持语义一致，错误码使用 Core 的稳定错误模型。
- 可观测性包使用 optional peer dependency 提供 OpenTelemetry 集成；结构化日志接口保持轻量。
- 所有公开包遵循工作区的双模块构建、类型检查、包边界、安全检查和发布干跑要求。

### 7.4 非范围

- Hono/Elysia 适配器、异步 Cookie 契约与边缘运行时支持。
- 在线会话查询、批量下线、JWKS、更多 Store 和安全策略扩展。
- 管理后台、OAuth2/OIDC 客户端或 Server。
- 修改 JWT 生命周期、临时 Token 原子消费或既有 Store 契约的业务语义。

### 7.5 假设与待验证项

| 假设 | 验证方式 |
| --- | --- |
| Fastify 的同步 Cookie 插件满足 v2.x Cookie 契约。 | Cookie E2E 覆盖读取、写入和未注册插件错误。 |
| Fastify `preHandler` 能覆盖路由策略所需的认证时机。 | 覆盖全局 Plugin、路由级策略和公开路由 E2E。 |
| 现有审计事件字段足以支持初始日志、追踪和指标。 | 用所有事件类型编写映射测试和示例。 |
| 实例化 Core 契约不破坏现有静态 API。 | 运行完整 NestJS、Express、Core 回归测试。 |

## 8. 发布计划

v2.3 按三个递进阶段交付，预计一个短迭代完成。R1 是 R2 的前置条件；R3 可以与 R1/R2 并行推进。

| 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| 阶段一：Core 契约 | 完成 `core-instance-contract` OpenSpec、Core API、兼容测试和迁移文档。 | `XltInstance` 可供适配器使用，既有 API 回归通过。 |
| 阶段二：Fastify | 完成 Plugin、桥接、类型、路由策略、E2E、示例和 README。 | Fastify 支持矩阵全部通过，包可独立发布。 |
| 阶段三：可观测性与发布 | 完成 exporter、日志/指标示例、脱敏测试、文档、CHANGELOG 和发布干跑。 | 所有质量门禁与发布检查清单通过。 |

首个 v2.3 版本只包含 R1、R2、R3。Hono 适配器和会话管理增强保留给 v2.4，且必须继续遵守 v2.2 的同步 Cookie 决策。
